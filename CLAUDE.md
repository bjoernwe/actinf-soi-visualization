# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An interactive explainer that reframes the classical meditation "progress of insight" stages (Baseline → Access → A&P → Dissolution → Dark Night → Equanimity → …) as **hierarchical predictive inference**. A Vite + TypeScript + Lit build, multi-page (each page is its own static HTML entry sharing one component library), no runtime dependencies except Lit and Google Fonts. The walkthrough is the main page (`src/pages/index/`); `component-demo` is a scaffold page proving the diagram is reusable with a different layer count, not authored model content.

- **A page is a self-contained pair under `src/pages/<name>/`: `<name>.html` + `<name>.ts`.** The `.ts` file exports one `Page` (a `DiagramConfig` + `Stage[]` plus the header copy — `eyebrow`/`heading` as Lit `TemplateResult`s, so inline markup like `<em>`/`<b>` survives). The `.html` is the entry point: `<head>` (fonts, the stylesheet, `<title>`), a `<div id="app">`, and an inline `<script type="module">` that imports `PAGE` from `./<name>` and `render()`s `<page-scaffold>` with it — reading the `.html` top to bottom shows exactly what's rendered and where its content comes from, instead of wiring implicitly through a separate bootstrap file. Add a page by adding the folder and a line in `vite.config.ts`'s `PAGES` map.
- `src/pages/styles.css` — all styling, shared by every page; the design-system tokens live in `:root`.
- `src/components/model/` — the authoring model, shared by every page: `model.ts` (the intensity system: `Level`, `IntensityValues`, the `INTENSITY` table, `MAX_BREADTH`, the pred/err `COLORS`), `diagram.ts` (`Layer`, `DiagramConfig`, `gapIds()`: what makes a diagram's layer constellation data instead of hardcoded), `stages.ts` (the authoring **types** — `Stage`, `Comment`, `Flow`, … — and `validateStage()`; no content lives here), `page.ts` (the `Page` descriptor type: `{ eyebrow, heading, config, stages }`, the whole of what one page is).
- `src/components/` — Lit components. `<page-scaffold>` (the page shell: header + rail + diagram, owns a `StageRouter`) and `<stage-rail>` are light-DOM, via `LightDomElement` (`light-dom-element.ts`: `createRenderRoot() { return this; }`), so the global `:root` tokens and `styles.css` page chrome apply directly. `<flow-diagram>/` groups the diagram subtree, which is Shadow DOM instead — each component carries its own `static styles`: `flow-diagram.ts` (`<flow-diagram>`, a pure translator from a `DiagramConfig` + `Stage` into the tree below, no geometry of its own), `flow-section.ts` (`<flow-section>`, one per gap plus the intake region: its own canvas, tween, particle pool, and comment placement), `tier-layer.ts` (a layer box, plus its own docked comment if the active stage has one), `comment-note.ts` (a comment's look — skin, accent, entrance animation — positioned by whichever parent hosts it). `shared-styles.ts` holds the small style fragments (`monoLabel`, `commentVoice`) shared across that subtree's `static styles`.
- `src/components/stage-router.ts` — `StageRouter`, a Lit `ReactiveController`: current-stage index, hash routing (both directions), arrow-key nav, and dev-time `validateStage()`. Owned by `<page-scaffold>`; registers/tears down its `window` listeners in `hostConnected`/`hostDisconnected`.

## Running

`npm install`, then `npm run dev` for a Vite dev server with HMR — pages are served at their nested path, e.g. `/src/pages/index/index.html` (there is no root `/` entry; the dev server has no index at the project root). `npm run build` (runs `tsc` first, then `vite build` once per page, per `vite.config.ts`'s `PAGES` map) produces a static `dist/` with one flat, self-contained html file per page (`dist/index.html`, `dist/intro.html`, `dist/component-demo.html`) — a `flattenPageHtml` plugin in `vite.config.ts` moves each page's build output from its nested source path back to `dist/`'s root after build, since these are meant to be opened/hosted directly. There is no lint or test step. `file://` no longer works directly — it needs the dev server or a built `dist/`.

## Audience & tone (this shapes all copy)

Readers are **dual-literate**: they know MCTB / Dharma Overground stage vocabulary (A&P, dark night, equanimity, cessation) *and* the basics of predictive processing / active inference (prior, prediction error, precision, model update). Do not explain those primitives — use them. Register is precise, unhurried, pragmatic-dharma: mechanistic and falsifiable-where-possible, never breathless or mystical. Existing stage copy is the style reference.

## The model being visualized

Two coordinates only — **S (solidity)** = precision of object-layer priors, and **O (opacity)** = how much experience is seen *as construction*. A third coordinate, **Realness (R), was tried and deliberately dropped — do not reintroduce it.** O has two regimes that carry most of the story: *effortful* opacity (fragile, policy-driven, fails under load — through Dissolution/Dark Night) vs *learned* opacity (a trained-in structural prior, effortless — Equanimity).

Visual grammar, load-bearing and non-negotiable: **predictions flow DOWN (periwinkle `--pred`), prediction errors flow UP (ember `--err`)**. "Blue falls, orange rises." Do not repurpose these two colors. Low S is *progress* in this model, not failure — never render dissolution as "bad."

Deep background on the per-stage claims (what each stage asserts in S/O terms, why the *transitions* are where the model lives) is in `doc/HANDOFF-for-visualization.md` and `doc/HANDOFF-stages.md`. Read them before writing or changing stage copy. **Caveat:** those docs predate the current engine and describe an older `p`-param scheme (`g0p/g0e`, `inR`, …); the code below is the source of truth for mechanics.

## Code architecture

**A page is a `Page` descriptor (`components/model/page.ts`), rendered by `<page-scaffold>`.** `Page` is `{ eyebrow, heading, config, stages }`: the header copy, a `DiagramConfig`, and the `Stage[]` authored against it. `DiagramConfig` (`components/model/diagram.ts`) is just `{ layers: Layer[] }` — an ordered list of `{ id, title, sub }`. Gap ids are positional: `g0` sits between `layers[0]`/`layers[1]`, etc. (`gapIds()`). A page's `.ts` (`src/pages/<name>/<name>.ts`) exports one `Page`; its `.html` inlines the one-line bootstrap: `render(html\`<page-scaffold .page=${PAGE}></page-scaffold>\`, document.getElementById('app'))`.

**`<page-scaffold>` (`components/page-scaffold.ts`) is the composition root.** It renders the header from `page.eyebrow`/`page.heading`, a `<stage-rail>` bound to `page.stages` and the router's `current`, and a `<flow-diagram>` bound to `{ config: page.config, stage: page.stages[current] }`. It owns one `StageRouter` (a Lit `ReactiveController`, `components/stage-router.ts`) as a plain field — the router holds `current`, listens for the rail's `stage-select` event via a template binding, and calls `host.requestUpdate()` on change, so a stage change is an ordinary re-render, not manual DOM mutation. This replaced an earlier `mountPage()` free function that did the same wiring via `document.querySelector` and manual property assignment — gone now that the shell is a component instead of hand-copied HTML.

**`Stage` (types in `components/model/stages.ts`) is the spine.** The rail is generated from a page's `Stage[]` and `StageRouter.setStage(i)` swaps the active target. Each stage entry has:
- `streams` — for each of the diagram's gaps, a `down` and `up` intensity **level name** (`Level = 'low' | 'med' | 'high'`).
- `intake` — the region below the last layer: `in` (sensory inflow, up/error) and `out` (outward action, down/prediction), each a level name.
- `jit` (lateral churn) and `spd` (flow-speed multiplier).
- `comments: Comment[]` — a discriminated union, `GapComment | TierComment` (narrow with `'tier' in def`), so a gap-anchored vs tier-anchored annotation can't mix fields.

`Gap`/`Tier` are plain `string`, not literal unions — a diagram's actual gaps/tiers come from its `DiagramConfig` at runtime, not one fixed compile-time shape (there are two `DiagramConfig`s already, with different layer counts). `validateStage()` recovers that safety at dev time: it checks a stage's gap/tier references against its `DiagramConfig` and throws a stage-named error on a typo, instead of a silently dead stream or an unplaced comment. `StageRouter.hostConnected()` calls it under `import.meta.env.DEV` automatically — a page's bootstrap doesn't need to.

**Intensity is indirected through `INTENSITY` (in `components/model/model.ts`).** Level names resolve to four tweenable channels — `breadth` (band width, the primary cue), `rate` (bubbles/sec), `alpha`, `size` — so a level reads even in a still frame or grayscale. Each `<flow-section>` flattens its own `down`/`up` level names into numbers and tweens `live` → `target` via exponential approach (`k = 1 - exp(-dt·3.2)`) in its own `frame()`, so **transitions are themselves meaningful** and must be tuned per stage, not just the endpoints.

**`<flow-diagram>` (`components/flow-diagram/flow-diagram.ts`) is a pure translator, not an engine.** Given a `DiagramConfig` + `Stage`, it renders one `<tier-layer>` per layer and one `<flow-section>` per gap (plus one more for the intake region below the last layer), handing each its own slice of the stage: a tier gets its `dock` comment if the stage has one for it; a `<flow-section>` gets its `down`/`up` levels, `jit`/`spd`, and the `GapComment[]` anchored to its gap (or `'intake'`). It carries no geometry of its own — nothing here measures anything.

**`<flow-section>` (`components/flow-diagram/flow-section.ts`) is one flow region: the canvas between two tiers, or the intake region.** It owns its own canvas, particle pool, and tween. `down` always renders as the descending prediction lane (periwinkle) and `up` as the ascending error lane (ember) — the intake region reuses the exact same component (`down = stage.intake.out`, `up = stage.intake.in`), since outward action already reads as a prediction and sensory inflow as an error. **Its height is a plain CSS custom property** — `--flow-height` for a gap, `--intake-height` for the intake (both in `:root`, `styles.css`) — so changing one only changes that region; nothing else's layout is derived from it. A `ResizeObserver` on the host re-measures the canvas whenever its rendered size changes for *any* reason (viewport resize, a CSS var edit, a font swap, a sibling reflowing) — there is no cached height to go stale, which a `window`-resize listener alone can't guarantee.

**Comment placement is CSS, not measured geometry.** `<flow-section>`'s `:host` is a 3-column grid — left comment column, stream lane, right comment column — sized from `--stream-off` (`:root`) and `--max-breadth` (set by `<flow-section>` itself in `connectedCallback()` from `MAX_BREADTH`, the same `INTENSITY` value its canvas reads a full-breadth band from, so the CSS clearance and the widest the canvas can actually draw can't drift apart). A comment's `side` picks its column directly, and its inward accent (`pin-left`/`pin-right`) is applied by the template, not computed from live positions. `<tier-layer>` docks its own comment the same declarative way — `top: 50%; transform: translateY(-50%)` — so the browser centers it on actual content height instead of a JS-measured one. `<comment-note>` (`comment-note.ts`) owns only how a comment looks (skin, `pin-left`/`pin-right`/`.dock` variants, entrance animation), never where it sits.

**The diagram subtree is Shadow DOM; the page chrome stays light-DOM.** `<flow-diagram>`, `<tier-layer>`, `<flow-section>`, and `<comment-note>` each carry their own `static styles` rather than sharing rules from `styles.css`. `:root` custom properties still inherit through a shadow boundary — that's how `--tier-width`, `--flow-height`, `--intake-height`, `--stream-off`, and the color/font tokens reach in — but ordinary rules don't cross it, which is the point: nothing outside a component can accidentally style or be styled by its insides. **A bare-tag override (`tier-layer { --tier-width: … }`) has lower specificity than `:root` and silently loses to it regardless of source order** — the mobile breakpoint's `--tier-width` override re-declares it on `:root` inside the `@media` block instead, for exactly this reason. `<page-scaffold>` and `<stage-rail>` stay light-DOM via `LightDomElement` (`components/light-dom-element.ts`: `createRenderRoot() { return this; }`) for now; converting them is a separate, later decision, not bundled into this one.

## Working conventions

- **This build proceeds incrementally — extend the existing pattern, don't rewrite.** The page was deliberately stripped to a foundation; elements (precision indicator / π-meter, right-hand content panel, S/O gauges, cessation blink) return one stage/feature at a time. Do not re-add them wholesale.
- **Change one thing at a time; respect the module boundaries (types in `components/model/`, per-page content + bootstrap in `pages/<name>/`, the diagram subtree in `components/flow-diagram/*.ts`, shell in `components/page-scaffold.ts`/`stage-router.ts`); keep diffs small.** Commit at each step.
- A new page is a folder `src/pages/<name>/` containing `<name>.ts` (a `Page`: `DiagramConfig` + `Stage[]` + header copy) and `<name>.html` (`<head>` + `<div id="app">` + the inline bootstrap script), plus a line in `vite.config.ts`'s `PAGES` map. It should not need changes to `components/page-scaffold.ts` or `components/flow-diagram/`.
- Reuse the `:root` CSS variables — don't hardcode colors. `--gold` (precision) and `--calm` (learned-opacity accent) are currently unused, reserved for when those elements return.
- `prefers-reduced-motion` needs a static fallback as `<flow-section>`'s rendering grows (earlier builds rendered static line-thickness instead of streaming dots) — re-add it rather than leaving reduced-motion readers with a dead diagram.
- When a change touches the *model's claims* (not just styling), surface the interpretive choice to Björn rather than silently picking one. Two open modeling items are flagged in the handoff docs: how A&P reads in pure S/O now that R is gone, and the precision-encoding scheme (error-gain vs prior-confidence).
